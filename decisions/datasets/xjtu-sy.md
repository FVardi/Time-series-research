# Decisions — XJTU-SY bearing data

Dataset-specific decisions for the XJTU-SY run-to-failure bearing data (Xi'an Jiaotong University and Changxing Sumyoung Technology; https://github.com/WangBiaoXJTU/xjtu-sy-bearing-datasets). Index: `../../DECISIONS.md`. Adopted by D189.

## 2026-11-02 — D191: XJTU-SY tasks and derived labels
**Decision:** XJTU-SY is used for several tasks on the same frozen representations, each with the harness probe that fits it. The dataset provides run-to-failure recordings, not health labels; all labels below are derived in the pipeline from the recording times, and the stored data stay as recorded (D5).
1. *Fault element* (classification): the failed element per bearing, if the dataset's documentation lists it (to be confirmed at download).
2. *Remaining useful life* (regression, D58/D59 probe): piecewise-linear target — constant before the first prediction time (FPT), then decreasing linearly to 0 at the end of the run; normalised to [0, 1] per bearing. Metrics: the regression metrics of the harness (MAE, R²) plus RMSE.
3. *Health stage / detection* (classification, and the anomaly protocol of D192): two stages, healthy (before FPT) and degrading (after FPT).
4. *Health indicator* (label-free): the D192 anomaly score of each window against the bearing's own early-life windows, evaluated with monotonicity, trendability and prognosability (Coble & Hines, 2009; exact definitions to be taken from the source at implementation).
FPT (one definition for tasks 2–4): the 3σ rule on the root-mean-square value — FPT is the first time the RMS exceeds the mean + 3 standard deviations of an early-life reference segment. Open, settled after looking at the data: the reference segment length, the channel(s) used, and how many consecutive exceedances are required (guard against single spikes).
Split by bearing (D121); conditions and number of held-out bearings decided with the configuration.
**Alternatives considered:** Linear remaining-useful-life target from the start of the run (penalises healthy early life). More than two health stages (no common definition). FPT by fixed fractions of life (ignores the large spread of bearing lives).
**Rationale:** User delegated the choice to Claude (2026-11-02), asking for the most widely used and/or most flexible options. The piecewise-linear target with an FPT from a 3σ rule is a common choice in bearing prognostics; one FPT definition keeps the tasks consistent; all labels are derived, so they can be changed without reconverting.

*Note (2026-11-03): task 1 confirmed. Table 2 of `Introduction_to_XJTU-SY_Bearing_Dataset.pdf` (in the archive) lists the fault element per bearing: outer race 8 (1_1, 1_2, 1_3, 2_2, 2_4, 2_5, 3_1, 3_5), inner race 3 (2_1, 3_3, 3_4), cage 2 (1_4, 2_3), combined 2 (1_5: inner and outer race; 3_2: inner race, ball, cage and outer race). Classes are small and unbalanced for a split by bearing, and the label describes the end of life, not the healthy start; both to be handled in the task configuration. Bearing type LDK UER204; test ended when the vibration amplitude exceeded 10 × the normal-stage maximum.*

## 2026-11-03 — D193: XJTU-SY raw data stored as downloaded (packing superseded by D213)
**Decision:** The XJTU-SY data are stored unchanged in `data/raw/xjtu_sy/` as downloaded from the authors' Google Drive (linked from https://github.com/WangBiaoXJTU/xjtu-sy-bearing-datasets): the six-part RAR archive (`Data/`, 9,236 CSV files, 12.2 GB unpacked; one CSV per minute, horizontal and vertical vibration, 32,768 samples at 25.6 kHz), the read-me files, `Important References/` and `Photographs/`. The archive is kept packed, as for Paderborn (D47); the conversion reads from it. No licence is stated; publications must cite Wang, Lei, Li and Li (2020), IEEE Transactions on Reliability 69(1), 401–412, doi 10.1109/TR.2018.2882682.
**Alternatives considered:** Unpacking the archive (12.2 GB of CSV next to the 4.4 GB archive).
**Rationale:** Follows D47 and D5 (raw data as recorded). Downloaded by the user (2026-11-03).

*Note (2026-11-04): the data are now unpacked in `data/raw/xjtu_sy/XJTU-SY_Bearing_Datasets/<condition>/<bearing>/<n>.csv` (D213); the archive parts were deleted.*

## 2026-11-05 — D224: XJTU-SY conversion: dataset documentation, otherwise harness conventions
**Decision:** Where the dataset's documentation and the literature using it have a standard, it is followed; otherwise the harness's conventions (D1–D6) and the usual time-series practice. Sources: `Introduction_to_XJTU-SY_Bearing_Dataset.pdf` (in the dataset folder; "intro") and Lei et al. (2019), J. Mech. Eng. 55(16), doi 10.3901/JME.2019.16.001 (in `Important References/`).
1. *Signals:* both accelerometer channels, horizontal and vertical, 25.6 kHz (intro Section 2.4); channel names as in the CSV header, `Horizontal_vibration_signals` and `Vertical_vibration_signals`.
2. *Hierarchy:* one run per bearing (one run-to-failure test; 15 runs, run ID e.g. `Bearing1_1`); each CSV (one 1.28 s sample of 32,768 points) one capture, `m0001`…`m2538` (file number, zero-padded); one stream (the two accelerometers share a clock).
3. *Timing:* capture start time nominal, (n − 1) × 60 s, with `timing_accuracy` "nominal: 1 min sampling period from the documentation; no timestamps in the files". Files are named in sampling order (Lei et al., 2019, Section 1.3); the files carry no timestamps, and their modification times (2019-01-31, about 20 s per bearing) are export times, not used.
4. *Operating condition:* nominal speed (2,100 / 2,250 / 2,400 rpm), shaft frequency (35 / 37.5 / 40 Hz) and radial force (12 / 11 / 10 kN) per capture in the telemetry table (intro Section 2.3).
5. *Per-capture columns (D31):* bearing, condition (folder name, e.g. `35Hz12kN`), file number, fault element verbatim from intro Table 2 (class grouping left to the task configuration, D191), `identical_to`. No derived labels; first prediction time, remaining useful life and health stages are derived in the pipeline (D191).
6. *Run extras:* documented lifetime (intro Table 2), L10 range (Lei et al., 2019, Table 3), bearing type LDK UER204 and its geometry (intro Table 1), sensors (2 × PCB 352C33 on magnetic mounts at 90°, DT9837 acquisition unit; Lei et al., 2019, Section 1.2), stop criterion (10 × A_h, intro Section 3).
7. *Units:* `g`. Not stated in the files or the intro's text; Lei et al. (2019) Section 3.2 gives amplitudes "up to 50 g (g = gravitational acceleration)" and the intro's Fig. 4 axes read "Amplitude (g)"; the largest value in the data is 54.4. The source is recorded in the run's extras.
8. *Status and type:* `final` (public benchmark); 64-bit floats as in the files (scale 1, offset 0; D6): the CSVs hold 17 significant digits, values are not on an exact integer grid and not exactly representable in float32. Parsed with pandas 3's default parser, which reads them back exactly (checked against Python's `float()` in `tests/test_xjtu_sy.py`). Source identification per D24 as for Paderborn: file name pattern, total size, latest modification time.
9. *Quirks:* recorded, not fixed: gaps in the file numbering, file counts differing from intro Table 2, unusual sample counts, NaN values, exact copies within a bearing; an unexpected header or column count stops the conversion. A read-only scan of all 9,216 files before conversion (2026-11-05) found none: one header throughout, 32,768 × 2 values per file, no NaNs, no duplicate files, numbering 1…N without gaps, counts as in Table 2.
**Alternatives considered:** Short channel names (`horizontal`, `vertical`). One run per CSV (9,216 runs) or per condition (3 runs). No start time (file number only). Units `unknown` (as Paderborn, where nothing is stated).
**Rationale:** User's decision (2026-11-05): approved as proposed; stay as close as possible to the literature standard for this dataset, otherwise to general time-series practice. A run is one test and a capture one uninterrupted acquisition (D1), matching how the dataset is documented and used (each bearing a run-to-failure sequence of one-minute samples). The nominal start time is what the remaining-useful-life labels of D191 need.

*Note (2026-11-05): item 8's parser was wrong on the project environment. pandas 3.0.6 (the version in `uv.lock`) does not read the 17-digit values exactly with its default parser (differences of up to 6,332 ulp, relative error below 1e-12); the check had been done with pandas 3.1.1, where it is exact. The first conversion was therefore not "as recorded" (D5) and was deleted; the reader now parses with Python's `float()` (correctly rounded on every platform, independent of the pandas version) and the data were reconverted. Found by the full comparison of all 9,216 files after conversion.*
