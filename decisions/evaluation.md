# Decisions — evaluation

Evaluation tasks, protocols, probes and metrics. Index: `../DECISIONS.md`.

## 2026-10-06 — D13: Tests are chosen per question and per dataset; full grid within a study; built incrementally
**Decision:** Not every test is run for every method. Each test must answer a stated research question. Tasks (regression, classification, anomaly detection) follow from each dataset's labels; protocols (frozen probe, fine-tuning, transfer to an unseen domain) are used only where they answer a question (e.g. fine-tuning where comparison with published results requires it; transfer only on datasets built for it). Within a study, the test grid is fixed in the study plan before running, and every method fills every cell; a cell a method cannot run is reported as missing with the reason, never dropped. The grid is built incrementally: comparisons are added only when shown to be necessary. The Step 1 grid discussed on 2026-10-06 is preliminary and not decided.
**Alternatives considered:** Running every task and protocol for every method and dataset (full factorial; hundreds of runs, most answering no specific question). Choosing tests per method (invites cherry-picking).
**Rationale:** Keeps comparisons fair and the number of runs proportionate to the questions asked.

## 2026-10-07 — D26: Evaluation protocol for the first slice (TS2Vec on FordA)
**Decision:**
1. *Two probes on the same frozen representations* (one 320-dimensional vector per series, max-pooled over time as in TS2Vec). (a) Reproduction check: TS2Vec's own protocol — RBF-kernel SVM, C chosen by 5-fold cross-validation on the training set over 10⁻⁴…10⁴ and ∞ (exactly as in the official code). (b) Harness probe: logistic regression with L2 regularisation on features standardised with training-set statistics, C chosen by 5-fold cross-validation on the training set over 10⁻⁴…10⁴.
2. *Test set used once.* All choices (probe C) are made by cross-validation inside the training set. No checkpoint selection: TS2Vec trains for a fixed number of iterations.
3. *Metrics:* accuracy and macro-F1.
4. *Seeds:* 3. The seed controls TS2Vec's initialisation and random crops; probes are deterministic.
5. *Label budgets:* 1 %, 10 % and 100 % of the training labels for the probes. Pretraining always uses all training inputs (without labels).
6. *Reproduction criterion:* the published 0.936 accuracy (TS2Vec paper, batch size 8) must lie within our mean ± 2 standard deviations over seeds; if the spread is very small, a difference of up to 1 percentage point is accepted. If it fails, investigate before going further.
**Alternatives considered:** Only the plan's logistic-regression probe (no comparison with the published number). TS2Vec's own logistic regression (no tuning of C). 100 % labels only (label budgets deferred).
**Rationale:** (a) validates our wrapped TS2Vec against the published result (D10); (b) is the harness's standard probe from the research plan. Choosing everything inside the training set keeps the test set clean.

## 2026-10-07 — D29: Label subsets and probe cross-validation details
**Decision:** For label budgets below 100 %, a new stratified random subset of the training labels is drawn for each seed (using that seed), so the spread over seeds includes the effect of which labels were drawn. The logistic-regression probe chooses C by cross-validated accuracy (scikit-learn's default scoring for classifiers), with `max_iter=10000` so the solver converges.
**Alternatives considered:** One fixed subset per label budget shared by all seeds (spread would reflect only pretraining randomness). Macro-F1 as the cross-validation score.
**Rationale:** Reported spread reflects both sources of randomness a user of the method would face; accuracy matches the reproduction metric.

## 2026-10-08 — D34: Change detection is not used as a test
**Decision:** Unsupervised change detection (is the bearing still in its reference state?) is not one of the harness's evaluation tasks. Lubrication condition is evaluated through supervised targets (e.g. κ, discrete lubrication conditions, Stribeck regions, degradation mechanisms), whichever is chosen once the data allow it.
**Alternatives considered:** Change detection as a fourth task type alongside regression, classification and ordinal classification (needs no labels; would fit unlabelled field data).
**Rationale:** User's decision (2026-10-08).

## 2026-10-08 — D40: Label budgets 1 %, 10 % and 100 % throughout Part 1
**Decision:** All Part 1 tests use the three label budgets 1 %, 10 % and 100 % of the training labels for the probes, as in D26 for the first slice; subsets drawn as in D29.
**Alternatives considered:** Fewer budgets outside the FordA slice (fewer runs, but less information on label efficiency, the main argument for SSL).
**Rationale:** User's decision (2026-10-08).

## 2026-10-08 — D45: Frozen-probe diagnostic of our TF-C encoders on FD-B
**Decision:** Diagnostic (`scripts/probe_tfc.py`, `configs/probe_tfc_fd.yaml`): the pretrained encoders of our TF-C run (D41, D42; run `20261008_142751_tfc_fd`, 5 seeds) are frozen; their representation [z_T; z_F] is probed with both harness probes (D26) trained on the 60 FD-B training windows and scored once on the FD-B test set. Label budget: 100 % only, as an exception to D40 for this dataset: 1 % of 60 labels is less than one window, and 10 % (2 per class) is too few for the logistic-regression probe's 5-fold cross-validation. Reference: an untrained encoder of the same architecture, initialised with the same seeds, probed the same way.
**Alternatives considered:** 100 % and 10 % with only the SVM probe at 10 %. A different cross-validation rule for small label sets. No untrained reference (then it cannot be told whether pretraining helped).
**Rationale:** User's decision (2026-10-08). Separates "pretraining learned little" from "fine-tuning too short or selection too noisy" (our TF-C: 0.706 ± 0.112 accuracy vs 0.893 published), without new training.

## 2026-10-08 — D46: Baseline: probes on the plain |FFT| spectra of FD-B
**Decision:** Baseline (`scripts/probe_spectrum.py`, `configs/probe_spectrum_fd.yaml`): both harness probes (D26) trained directly on the full FFT magnitude spectrum of each FD-B training window (the input TF-C's frequency branch receives, D41 item 2), no encoder; 100 % of the 60 training labels (as D45); scored once on the FD-B test set. The probes are deterministic, so there are no seeds.
**Alternatives considered:** No baseline (then it cannot be told whether FD-B separates methods at all).
**Rationale:** User's decision (2026-10-08). The untrained-encoder SVM probe reached 0.973 (D45); if the plain spectra score as high, FD-B cannot separate the methods.

## 2026-10-09 — D49: Feature baseline: the MSSP statistics per octave band (details open) (partly settled by D50)
**Decision:** A hand-crafted feature baseline is added as a method without training (`encode(X)` returns features; the harness probes go on top, logistic regression for classes and a ridge probe for regression, the latter still to be decided). Features: the 14 statistics of the MSSP feature code (`publication-ceramicspeed-dataset/src/ceramicspeed/features.py`: RMS, skewness, kurtosis, crest, shape and margin factor, Hjorth mobility and complexity; dominant frequency, spectral centroid, bandwidth, skewness, kurtosis and flatness), computed per band of an octave filter bank instead of the MSSP pipeline's hand-picked bands. The MSSP pipeline is not reproduced as such (it is unpublished). Open: octave or third-octave, band edges, frequency range, filter implementation, window, and whether a broadband set is kept.
**Alternatives considered:** Octave-band energies only (simpler, but not the features). The MSSP pipeline as it stands (hand-picked bands, rig-specific).
**Rationale:** User's decision (2026-10-09). Same statistics, but a neutral band choice that applies to every dataset.

## 2026-10-09 — D50: Feature baseline details: third-octave bands, Butterworth filters, broadband set kept (band spacing superseded by D53)
**Decision:** For D49: third-octave bands; each band filtered with a zero-phase Butterworth band-pass of order 5 (as `bandpass_filter` in the MSSP code); the 14 statistics are also computed on a broadband version of each signal. Still open: band-edge convention and the frequency range per sensor (the range follows from D52).
**Alternatives considered:** Full octaves (only 3–4 bands in the AE range). FFT-bin summation instead of filters. No broadband set.
**Rationale:** User's decision (2026-10-09).

## 2026-10-09 — D53: Feature baseline uses full-octave bands, base 10, standard edges (bands per sensor superseded by D60)
**Decision:** The filter bank of D49/D50 uses full-octave bands, base 10 (centre frequencies f_m = 1 kHz · 10^(0.3·x), edges f_m · 10^(±0.15)), with the standard edges unchanged (outer bands are not cut at the sensor's range limits). With the current ranges: AE 4 bands (centres 63.1, 126, 251, 501 kHz; 44.7–708 kHz in total); US 8 bands (centres 1.0 … 126 kHz; 0.71–178 kHz in total). Supersedes the third-octave spacing in D50 (third-octave bands give 490 features for AE + US). The frequency range per sensor still follows from D52.
**Alternatives considered:** Third-octave (12 AE / 21 US bands). Half-octave (8 / 15). Cutting the outer bands at the range limits, or dropping bands mostly outside the range.
**Rationale:** User's decision (2026-10-09). Fewer, wider bands: 14 statistics × (bands + broadband) gives 70 AE + 126 US features.

## 2026-10-09 — D54: Feature baseline: four US bands; features over whole sweeps (US bands superseded by D57)
**Decision:** (1) The four lowest US octave bands (centres 1.0–7.94 kHz) are dropped, leaving four US bands (centres 15.8, 31.6, 63.1, 126 kHz; 11.2–178 kHz), the same number as for AE. The US broadband set starts at 0 Hz (upper limit from D52); content below 11.2 kHz is thus only in the broadband statistics. (2) The 14 statistics are computed over whole sweeps (one feature vector per sweep and sensor), as in the MSSP code.
**Alternatives considered:** All eight US bands. Features per window (the unit the SSL methods see).
**Rationale:** User's decision (2026-10-09). The lowest bands are too low; equal band count for both sensors.

## 2026-10-09 — D57: Feature baseline: seven US bands (lowest kept, highest dropped) (bands per sensor superseded by D60)
**Decision:** US octave bands: centres 1.0, 2.0, 3.98, 7.94, 15.8, 31.6, 63.1 kHz (0.71–89.1 kHz); the 126 kHz band is dropped. Supersedes part (1) of D54. AE keeps its four bands (D53).
**Alternatives considered:** Four US bands 15.8–126 kHz (D54): the strongest US content (below 8 kHz, MSSP config) would only enter through the broadband statistics.
**Rationale:** User's decision (2026-10-09).

## 2026-10-09 — D58: Ridge probe for regression, regularisation chosen on a grid
**Decision:** Regression targets (κ) are probed with ridge regression; the regularisation strength is chosen by cross-validation over a fixed grid (deterministic, like the logistic probe, D26), not by Optuna. The label budgets of D40 (1 %, 10 %, 100 %) also apply to regression. Open: grid range, cross-validation grouping on the rig (D56), standardisation and metrics (research plan: MAE and R²).
**Alternatives considered:** Optuna (useful for several hyperparameters, here only one; adds a seed).
**Rationale:** User's decision (2026-10-09).

## 2026-10-09 — D59: Ridge probe details
**Decision:** For D58: features standardised with training-set statistics; regularisation strength chosen by cross-validation over the grid 10⁻⁴ … 10⁴ (powers of ten, as the logistic probe's C grid, D26); on the rig, cross-validation folds grouped by acquisition hold with "twin" holds merged (as the MSSP `grouping.py`); metrics MAE and R² (research plan).
**Alternatives considered:** Ungrouped folds (near-duplicate sweeps of one hold in both fold parts bias the choice of regularisation).
**Rationale:** User's decision (2026-10-09).

## 2026-10-09 — D60: Feature bands per sensor after the band check (D52) (AE bands superseded by D61)
**Decision:** AE: nothing below 50 kHz is used (its origin is unknown; the AE coupler high-passes at 50 kHz), and the top octave band (centre 501 kHz, 355–708 kHz) is excluded as mostly noise. AE bands: centres 63.1, 126, 251 kHz (edges 44.7–89.1, 89.1–178, 178–355 kHz). US: the 126 kHz band (89.1–178 kHz) is included again, because the band check shows rpm-dependent content there. US bands: centres 1.0, 2.0, 3.98, 7.94, 15.8, 31.6, 63.1, 126 kHz (0.71–178 kHz). Supersedes the band lists of D53 (AE) and D57 (US). Open: the lowest AE band's edge at 44.7 kHz lies below 50 kHz; the AE broadband range (50 kHz up to 355 kHz, or up to about 560 kHz where the band check still shows signal).
**Alternatives considered:** AE bands from D53 (including 501 kHz); US bands from D57 (up to 89.1 kHz).
**Rationale:** User's decision (2026-10-09), based on `runs/20261009_085307_band_check_herning`. Caveat: whether US content above about 40 kHz is bearing signal or electrical interference is open (QUESTIONS.md, Q3).

## 2026-10-10 — D61: AE feature bands as octaves from 50 kHz, top band ending at 560 kHz
**Decision:** AE bands start at exactly 50 kHz and double: 50–100, 100–200, 200–400 kHz, plus a shortened top band 400–560 kHz, ending where the band check (D52) shows the AE signal stops. AE broadband set: 50–560 kHz (the range these bands cover). An exception to the base-10 standard edges of D53 for AE; US keeps its base-10 bands (D60). Supersedes the AE bands of D60.
**Alternatives considered:** Three bands 50–400 kHz (drops the weak signal 400–560 kHz). Top band ending at 600 kHz (MSSP config limit). Base-10 bands (lowest band edge at 44.7 kHz, below the 50 kHz limit).
**Rationale:** User's decision (2026-10-10). Nothing below 50 kHz (unknown origin), nothing above about 560 kHz (noise, D52).

## 2026-10-16 — D70: Datasets for the Step 1 comparison; FD-A/FD-B only for the TF-C reproduction (CWRU open point settled by D115)
**Decision:** The Step 1 comparison of methods uses FordA (sanity check against published numbers; classification), the raw Paderborn bearing data split by bearing (leakage-safe vibration faults, including a held-out operating condition, research plan 1.4; classification), and the Herning rig data (target data; κ regression). Within the study, every method is run on every one of these datasets (D13); a method that technically cannot run on a dataset is reported as missing with the reason. FD-A/FD-B (TF-C's windows, D39) are used only as the record of the TF-C reproduction (D35–D44), not as a benchmark: FD-B is solved by the plain spectrum (0.999, D46) and its leakage cannot be checked (D39). Open: FordB (cheap second reproduction check; adds little scientifically) and CWRU (comparability with the literature; few recordings per fault and load), see QUESTIONS.md Q4.
**Alternatives considered:** Applying every method to every dataset and protocol, including FD-A/FD-B and their transfer protocol (protocols chosen by the papers, not by the research questions). FD-A/FD-B as plain classification like FordA (trivial, leakage unknown).
**Rationale:** User's decision (2026-10-16). Datasets and tasks follow the research questions; the transfer that matters (an unseen operating condition) is tested cleanly on Paderborn and, as a temperature hold-out, on Herning.

## 2026-10-16 — D75: Baselines the SSL methods must beat (item d partly superseded by D85)
**Decision:** Part 1 uses these baselines, each probed with the harness probes (D26 for classes, D58/D59 for regression) under the label budgets of D40: (a) *floor*: the most frequent training class, or the training mean of a regression target; (b) *raw samples*; (c) *|FFT| magnitude spectrum*; (d) *MSSP statistics* (the 14 statistics of D49); (e) *MiniRocket* (random convolution kernels, no training). In addition, (f) each SSL architecture *untrained*, initialised with the same seeds and probed the same way (as D45), as a control that separates what pretraining adds from what the architecture alone gives. The three axes are accuracy and macro-F1 (MAE and R² for regression), robustness to sparse labels (the D40 budgets) and speed (D79). Deferred: a supervised model trained from scratch on the labels only, and non-linear probes (random forest, gradient boosting) on the features.
**Alternatives considered:** catch22 instead of the MSSP statistics for (d) (published, neutral, but a second feature set beside the one used on the rig). Log magnitude for (c). Supervised from scratch now (needs its own set of training decisions).
**Rationale:** User's decision (2026-10-16). Each baseline answers its own question: (a) the bottom of the scale; (b) does SSL beat no representation; (c) does it beat a shift-invariant representation without learning (D46 showed FD-B is saturated by it); (d) does it beat domain knowledge; (e) does it beat the standard fast, training-free method for time series classification.

## 2026-10-16 — D76: Baseline inputs (item 3 partly superseded by D85; item 1's "values as loaded" superseded by D255)
**Decision:**
1. *Raw samples:* values as loaded (as recorded, D5), no per-series normalisation (it would remove amplitude, which matters for condition monitoring); channels concatenated. FordA is already z-normalised by the archive (D27).
2. *|FFT|:* one-sided spectrum (`numpy.fft.rfft`, bins 0 … N/2) per channel, linear magnitude, channels concatenated. D46's two-sided spectrum stays as recorded for the FD-B diagnostic.
3. *MSSP statistics:* the 14 statistics of `extract_features` in the MSSP code (`publication-ceramicspeed-dataset/src/ceramicspeed/features.py`), one vector per channel, concatenated. On datasets without a physical sampling rate (FordA) only the broadband set (the signal as loaded, no filter); on the rig the octave bands of D53–D61 plus the broadband set.
4. *MiniRocket:* official code (`angus924/minirocket`, commit 0b1c245) as a pinned submodule (D19), official settings (`num_features` 10,000, `max_dilations_per_kernel` 32), fitted on all training inputs without labels. It draws training examples at random to set its biases, so it is run with seeds. Its own probe (ridge classifier, as in the official README) is run next to the harness probes as a reproduction check, as `svm_ts2vec` for TS2Vec (D26).
**Alternatives considered:** Log magnitude, log(1 + |X|) (compresses the dynamic range; kept as an option). Two-sided spectrum as in D46 (duplicates every bin, which halves the effective L2 penalty on it). Per-series normalisation of the raw input.
**Rationale:** User's decision (2026-10-16).

## 2026-10-16 — D77: Baselines enter the harness as methods without training
**Decision:** Each baseline is a method module in `harness/methods/` (one file per baseline, D18) with the same interface as the SSL methods: `pretrain()` returns nothing or a fitted transform (MiniRocket), `encode(X)` returns the features. Baselines run through `scripts/pretrain.py` and `scripts/evaluate.py` unchanged, so probes, label subsets and metrics are the same code as for the SSL methods.
**Alternatives considered:** A separate script per baseline, like `scripts/probe_spectrum.py` (D46): simpler at first, but a second evaluation path that can drift from the first.
**Rationale:** User's decision (2026-10-16). One evaluation path for all methods (D10, D26).

## 2026-10-16 — D78: Same seeds as the SSL runs; differences reported paired per seed
**Decision:** On each dataset, baselines use the same seeds as the SSL runs (FordA: 0, 1, 2). Label subsets are drawn per seed (D29), so at every budget all methods and baselines are probed on exactly the same labelled series, and differences are reported paired per seed. Deterministic baselines are still run once per seed for this reason.
**Alternatives considered:** One run per deterministic baseline with its own subsets (unpaired; differences carry the subset noise).
**Rationale:** User's decision (2026-10-16). Paired differences are much tighter than comparing mean ± SD.

## 2026-10-16 — D79: Speed measured per stage (warm-up detail refined by D81)
**Decision:** Wall-clock time (`time.perf_counter`) is recorded per seed for (i) fitting or pretraining, (ii) encoding the training and test inputs (also given as series per second), (iii) fitting each probe at each label budget. GPU work is followed by `torch.cuda.synchronize()` before the clock is read. Each method runs on the device it would be used on (baselines on CPU, SSL methods on GPU); the hardware is written to the run folder. MiniRocket's first call compiles its code (numba); this is excluded by a warm-up call and its time recorded separately. The existing TS2Vec and T-Loss runs on FordA have no timings and are rerun with timing.
**Alternatives considered:** Everything on CPU (fairer for the encoding step, but not how the methods would be used). Timing only pretraining.
**Rationale:** User's decision (2026-10-16). Speed is one of the three axes (D75).

## 2026-10-16 — D80: Reporting against the baselines
**Decision:** Accuracy and macro-F1 as before (D26). Per label budget, each SSL method's paired difference (per seed, D78) to the best baseline at that budget is reported; "best" is chosen by test score, which favours the baselines (conservative for the SSL methods). A label-efficiency figure shows score against label budget (log x-axis). Time per stage (D79) in its own columns. All in a new result entry in `report/results.tex`, generated by `scripts/make_report.py` (D63).
**Alternatives considered:** Mean ± SD only (unpaired). A single summary number such as the area under the label-efficiency curve.
**Rationale:** User's decision (2026-10-16).

## 2026-10-19 — D81: MiniRocket details: own probe, reproduction target, seeding, compile time
**Decision:**
1. *Own probe* (`ridge_minirocket`): the official README's `RidgeClassifierCV(alphas=np.logspace(-3, 3, 10), normalize=True)`. scikit-learn has removed `normalize`; its documented replacement is used, which gives the same model: features standardised with training statistics and every alpha multiplied by the number of training series (a test checks the equivalence against the old normalisation done by hand).
2. *Reproduction target:* 0.950 accuracy on FordA (official `results/accuracy_ucr109_resamples.csv`, resample 0, taken to be the original train/test split; the repository does not say so explicitly; the mean over 30 resamples is 0.948). Criterion as D26 item 6.
3. *Seeding:* MiniRocket draws random numbers inside numba-compiled code, which `np.random.seed` does not reach. Before each fit, numba's generator is seeded with a number drawn from NumPy's generator (which `runs.set_seed` has seeded), so the run's seed fixes MiniRocket's choices.
4. *Compile time:* the official functions have explicit numba type signatures, so they compile (or load numba's cache) when the module is imported, not at the first call. The import time is recorded as the compile time (`compile.json`) instead of a warm-up call (refines D79); it is not counted as fit time.
5. Dependencies `numba` (and `antropy`, D82) added; with the locked numpy 2.5.3 no other version changes (numba 0.68 accepts numpy < 2.6). MiniRocket is GPL-3.0, which matters if its code goes into a publication copy (D11).
**Alternatives considered:** Standardising without scaling alpha (changes the effective penalty). Harness probes only (no reproduction check). Mean over 30 resamples as target (our run uses one split).
**Rationale:** User's decision (2026-10-19).

## 2026-10-19 — D82: MSSP statistics: the MSSP code itself; sampling rate 1 on FordA; both probes (FordA part superseded by D85)
**Decision:** The MSSP feature file is copied unchanged into `harness/methods/mssp_features.py` (verified identical to the source), so the statistics, including the Hjorth parameters from `antropy`, are exactly those of the MSSP code; `antropy` becomes a dependency. **Alternatives considered:** Reimplementing the statistics (risk of silent differences). Only the logistic probe for the feature baselines (an empty cell in the grid).
**Rationale:** User's decision (2026-10-19).

## 2026-10-19 — D85: catch24 as the generic feature baseline; MSSP statistics on the rig only (Herning part narrowed by D188)
**Decision:** The hand-crafted feature baseline (D75 d) on every dataset (FordA, Paderborn, Herning) is *catch24*: the catch22 features (Lubba et al., 2019) plus mean and standard deviation, computed with `pycatch22` (the authors' C implementation, GPL-3.0) per channel, channels concatenated. On Herning the MSSP statistics per band (D49–D61) are kept in addition, as the domain baseline. Supersedes D75 (d) and D76 item 3 for the public datasets, and the FordA part of D82 (MSSP is no longer run on FordA; `configs/mssp_forda.yaml` removed). Whether catch24 is also computed per frequency band on Herning is decided with the Herning step.
**Alternatives considered:** catch22 replacing MSSP everywhere (loses the domain baseline and the link to the MSSP paper). MSSP everywhere (weak and arbitrary on FordA: z-normalised series, no physical frequency). Plain catch22 (z-normalises each series, so it ignores level and amplitude, which matter on the rig). aeon's catch22 (no compiler needed, but forces numpy < 2.5 and scipy < 1.18 on the whole environment).
**Rationale:** User's decision (2026-10-19). catch22 is a published, neutral feature set chosen for discriminative power across many datasets, so it means the same on every dataset; the MSSP statistics answer the rig-specific question whether SSL beats the domain pipeline.

## 2026-10-19 — D86: PatchTST pooling diagnostic (mean and flatten from the saved models)
**Decision:** The PatchTST FordA run (`20261019_130910_patchtst_forda`, D74) scored 0.808 (SVM, all labels) and chance level at 1 % labels. To see whether taking the last patch's vector (D74 item 7) limits this, the saved models of that run are re-encoded, unchanged, with two other poolings: 'mean' (mean of the 41 patch vectors; 128 values) and 'flatten' (all patch vectors; 5,248 values). Same series, labels, seeds, probes and label budgets as the source run; evaluated with `scripts/evaluate.py`. Script `scripts/reencode_patchtst.py` (one run folder per pooling, `diagnostic_of` in its config, encoding times recorded as in D79); helper `patchtst.load()`. The results are a diagnostic; which representation counts as the PatchTST result is decided separately (D87).
**Outcome (2026-10-19):** run in a cloud copy (CPU; same library versions as the repo's .venv; 'last' reproduced within 5e-6): `runs/20261019_154248_patchtst_forda_mean` (SVM 0.875 ± 0.030, logreg 0.855 ± 0.045 with all labels) and `runs/20261019_154305_patchtst_forda_flatten` (0.847 / 0.851; representations not copied back, too large). With mean pooling, accuracy per seed follows the final pretraining loss.
**Alternatives considered:** Retraining with each pooling (pooling does not affect training; retraining would add GPU and learning-rate-finder variation between the compared encoders). Fine-tuning (a separate question of the evaluation protocol: D26 uses frozen encoders).
**Rationale:** User's decision (2026-10-19). Separates the representation read-out from the pretraining itself at almost no cost.

## 2026-10-19 — D89: Raw-samples baseline without the logistic probe

## 2026-10-20 — D90: catch24 computed with pycatch22 1.0.2; features that cannot be estimated stop the run

## 2026-10-17 — D93: Collapse diagnostics, logged every epoch (open settings and dead-dimension threshold settled by D94)
**Decision:** During pretraining, after every epoch, representations of a fixed set of windows are computed in evaluation mode and the following are written to `collapse.csv` in the run folder (one row per epoch and representation): effective rank (RankMe: exp of the entropy of the normalised singular values); the full eigenvalue spectrum of the covariance; the mean per-dimension standard deviation and the fraction of dimensions with standard deviation below ε; the mean pairwise cosine similarity; the SIGReg statistic (LeJEPA, arXiv 2511.08544), computed without gradients and not used in the loss. The functions live in `harness/diagnostics.py` (D91). The measures only detect collapse; nothing is enforced. Open: which representations are logged (h_T, h_F, z_T, z_F, [z_T; z_F]; augmented views or not; alignment between a view and its augmented version), the value of ε, the SIGReg settings (number of directions, t-grid, weighting; to be taken from the official LeJEPA code), and the window set (first validation run on FordA, details to be decided).
**Alternatives considered:** Effective rank only (cheaper, but does not show how the spectrum collapses or distinguish complete from dimensional collapse). Regularising against collapse straight away (VICReg or SIGReg in the loss; changes the method before its behaviour is known). Logging less often (may miss early collapse).
**Rationale:** User's decision (2026-10-17). TF-C's encoders sometimes collapse; logging the measures per representation shows where and when collapse starts (encoder vs projector, time vs frequency branch) before deciding whether to counter it.

## 2026-10-27 — D134: Random-init baseline: each method's untrained encoder, frozen and probed (probes superseded by D135)
**Decision:** For every method with an encoder (TS2Vec, T-Loss, TS-JEPA (masking fixed), PatchTST, TS-TCC, TF-JEPA, SimMTM, FreRA, TF-C (positives)), the untrained encoder is probed exactly like the trained one, to measure how much pretraining adds. Two variants (config key `random_init`): (a) `as_initialised`, the encoder as built; (b) `bn_from_train`, as (a), but every batch-norm layer the encoder passes through stores the mean and population variance of its input over the training series (repeated forward passes in evaluation mode, no gradients, weights unchanged; `harness/random_init.py`). (b) only for the methods with batch norm (PatchTST, TS-TCC, TF-JEPA, SimMTM, FreRA, TF-C); for the others it would equal (a). Representation: the method's own `encode()`, as in its trained runs. Seeds, probes and label budgets as in the method's trained config; `published_accuracy: null`. One config per method and variant, copied from the trained config (`configs/<trained config>_random.yaml`, `..._random_bn.yaml`); `tests/test_random_init.py` checks that each copy still matches its trained config apart from name, `random_init` and `published_accuracy`. Datasets: FordA, CWRU and Paderborn; the CWRU and Paderborn copies are made when the trained configs of those datasets exist. Details: PatchTST's learning-rate finder (D74) still runs in the untrained case, so the random numbers drawn before the model is built are the same as in the trained run; `pretrain_s` in timing.json is the building time plus, in (b), the batch-norm pass. Checked: for all nine methods (CPU, random data, FordA configs) the untrained encoder's parameters equal the trained run's parameters before its first optimiser step (for TF-JEPA the encode branches; its EMA target branches are not used by encode); the TF-C case is a test in `tests/test_random_init.py`.
**Alternatives considered:** Epochs or iterations set to 0 in a config copy (TS-TCC and SimMTM check their official configs and would stop; PatchTST's one-cycle schedule and the TS-JEPA/TF-JEPA schedulers may fail with 0 steps; the intent hidden in a number). Only (a), or only (b). A fresh random initialisation not tied to the trained run (loses the pairing per seed).
**Rationale:** User's decision (2026-10-27). Shows how much of each method's result comes from pretraining rather than from the architecture and the probe. (b) separates untrained weights from normalisation not adapted to the data: in evaluation mode a new batch-norm layer normalises with mean 0 and variance 1, whatever the data.
*Finding (not changed):* in our TF-C, building a `Branch` runs one forward pass of zeros in training mode to size the projector. This updates the encoder's batch-norm statistics (running variance 0.9 instead of 1, `num_batches_tracked` 1). Training is not affected, but variant (a) of TF-C starts from these statistics, not from 0 and 1.

## 2026-11-02 — D192: Anomaly-detection protocol (normal-only training)
**Decision:** Detection of departures from normal is evaluated with frozen representations, like the probes (D26):
1. *Fit*: embed the normal training windows (for DCASE, the source and target normal clips pooled).
2. *Score*: two anomaly scorers, both reported — (a) k-nearest-neighbour distance to the normal embeddings, k = 1, Euclidean on embeddings standardised with the normal set's mean and SD; (b) Mahalanobis distance to a Gaussian fitted on the normal embeddings (covariance shrinkage settled at implementation if the covariance is singular).
3. *Aggregate*: where the unit of evaluation is longer than a window (a DCASE clip, a recording), its score is the mean of its window scores.
4. *Metrics*: AUROC and pAUC (false-positive rate 0–0.1), threshold-free. On DCASE 2022 bearing as in the official evaluation: AUC per section and domain, pAUC per section, and the official score Ω (harmonic mean of all of them). No decision threshold.
5. *Where*: DCASE 2022 bearing; Paderborn (healthy bearings as normal); Ottawa UODS-VAFDC (healthy as normal; developing and faulty as anomalies, reported separately); XJTU-SY (healthy stage as normal, D191). Not CWRU (no healthy class, D125). Herning once nominal and off-nominal lubrication states exist.
Reconstruction error and outlier exposure are not used as scorers.
**Alternatives considered:** k > 1; Gaussian mixture, one-class SVM, isolation forest, local outlier factor (more settings). Reconstruction error (only generative or masked methods, not comparable across methods). Outlier exposure (needs a trained head on metadata labels, outside the frozen-encoder comparison). Separate scoring against source and target normals on DCASE.
**Rationale:** User delegated the choice to Claude (2026-11-02), asking for the most widely used and/or most flexible options. Distance in embedding space works for every method without training, k-NN needs no distributional assumption and uses the few target-domain clips directly, Mahalanobis is the common parametric counterpart; AUROC/pAUC/Ω make DCASE numbers comparable with the challenge.

**Decision:** On run-to-failure data (XJTU-SY; config `per_bearing: true`) the spectral probe (D244) also reports, for the ridge probe of every target, Pearson's correlation between predictions and targets within each test bearing (`results/<config name>_per_bearing.csv`: run, target, test bearing, number of windows, r). The probe itself is unchanged: trained on the training bearings, as before. The overall test R² stays the main measure.
**Alternatives considered:** Overall test R² only (on XJTU-SY dominated by the level offset between bearings: the floor's R² is about −4.6); R² within each bearing (still penalises the offset); Spearman's correlation (Pearson's r is the common choice for agreement between a prediction and a target); the measure on all datasets (on CWRU, HUST and Paderborn each test bearing is one fixed state with no trend, so a within-bearing correlation would mostly measure noise).
**Rationale:** User's decision (2026-11-12). The test bearings are not in the training data and each sits at its own spectral level; within a bearing the question is whether the representation follows how the spectrum changes over the bearing's life, the change that remaining-useful-life prediction rests on.
