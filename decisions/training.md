# Decisions — training

Method integration, pretraining and the training loop. Index: `../DECISIONS.md`.

## 2026-10-03 — D10: Two ways to integrate a method, one shared encoder boundary
**Decision:** The harness supports two kinds of method. (A) *Wrapped methods*: official code used as a black box behind an adapter that trains on unlabelled training data and exposes `encode(X)`; architecture, augmentations and loss are left untouched. (B) *Composed methods*: built from harness components — tokenizer, encoder, view generator (augmentations or masking), objective and a shared training loop — combined through configuration. Both produce the same artifact (an encoder checkpoint or stored embeddings), so evaluation is independent of how the encoder was trained. Safeguards for (B): (1) every composed counterpart of a published method must reproduce the official (A) result within the seed spread on one benchmark before it is used; (2) reimplemented components are tested against the official functions (same input and seed, same output); (3) components have no internal defaults — every parameter is set in the configuration; (4) the comparisons a study will make are written down before it is run. Which methods to implement first, and in which mode, is decided separately.
**Alternatives considered:** Wrapped methods only (faithful to published results, but no controlled swapping of objectives or views; Steps 2.4 and 3 of the research plan would require restructuring). Composed methods only (flexible, but no reference implementation to validate reimplementations against, and weaker comparability with published results).
**Rationale:** Step 1 of the research plan needs faithful baselines; Steps 2–3 need controlled comparisons in which only one component differs. A shared boundary lets both coexist. The added flexibility of (B) creates room for silent reimplementation errors, hidden defaults, invalid combinations and selective reporting; the safeguards address these.

## 2026-10-06 — D15: Plain PyTorch; scikit-learn for probes and simple baselines
**Decision:** Models and training loops are written in plain PyTorch, with the training loop written out explicitly. scikit-learn is used for probes and simple baselines.
**Alternatives considered:** PyTorch Lightning (less boilerplate, but hides the training loop).
**Rationale:** Readable, checkable code (code-style rule in CLAUDE.md).

## 2026-10-06 — D19: Official method code as pinned git submodules; modified versions as separate, named methods
**Decision:** Official method repositories (e.g. T-Loss, TS2Vec) are added under `external/` as git submodules pinned to an exact commit and are never edited. Our adapter in `harness/methods/` calls them. A fix needed only to make the code run (e.g. a changed library API) goes in the adapter, documented in a comment. A fix that must change the method's own code, or an improvement, is made in a copy under `harness/methods/`, under its own method name, with a header stating the original repository and commit and what was changed. The unmodified original stays available as the reference, and the modified version is validated against it (D10). Results from a modified version are always reported under its own name, never as the original method.
**Alternatives considered:** Copying official code into the repository (loses provenance; invites quiet edits). Installing from git at a pinned commit (clean, but most research repositories are not installable packages). Editing the submodule directly (mixes our changes with theirs and hides them).
**Rationale:** Records exactly which version was used, keeps the original as a reference for validation, and makes every modification visible and attributable.

## 2026-10-07 — D28: TS2Vec training settings for the first slice
**Decision:** TS2Vec is trained with the official defaults, all written explicitly in the config: learning rate 0.001, batch size 8, representation dimension 320, hidden dimension 64, depth 10, maximum training length 3,000, and the number of iterations given by TS2Vec's own rule (200 if the training data has at most 100,000 values, otherwise 600; 600 for FordA).
**Alternatives considered:** Tuning TS2Vec's settings (would no longer reproduce the published setting).
**Rationale:** The first slice must reproduce the published result before anything else.

## 2026-10-08 — D32: T-Loss on FordA
**Decision:** T-Loss is wrapped from its official repository (submodule `external/tloss`, commit 4aff592), using only its encoder training and encoding; evaluation runs through the harness probes (D26), whose SVM probe is the protocol behind T-Loss's published results. Settings (official, all in the config): batch size 10, learning rate 0.001, depth 10, 40 channels, kernel size 3, K = 10 negative samples, full-length comparisons, no early stopping, representation size 320 (internal size 160, as in the code and README; the paper swaps them), 2,000 training steps (paper, for K ≥ 10; the shipped default file says 1,500). T-Loss trains in 64-bit floats, as its code requires. Reproduction target: 0.928 accuracy on FordA (K = 10), with the D26 criterion; same probes, label budgets and seeds as D26. FordA as converted (D27).
**Alternatives considered:** 1,500 steps as in the default file (not the setting of the published number). Using T-Loss's own classifier code (relies on a scikit-learn option that has since been removed).
**Rationale:** A second reproduction check of a wrapped method on a dataset we already have, with a published number to compare against.

## 2026-10-08 — D35: TF-C study sequence
**Decision:** TF-C is added in steps, each giving the reference for the next: (1) reproduce the published TF-C result with the official code (FD-A → FD-B, as distributed by the TF-C authors); (2) apply the official TF-C to the full Paderborn bearing dataset, converted from the raw data; (3) implement our own version of TF-C (a separate, named method, D19) that corrects errors in the official code, and assess whether this changes the results meaningfully; (4) possibly compare one of the two versions with TS2Vec and T-Loss on FordA. The details of each step are decided separately.
**Alternatives considered:** Only FD-A → FD-B as distributed (no recording or bearing IDs, so leakage cannot be checked). Only the raw Paderborn data (no published number to validate against). TF-C directly on FordA (no published FordA number to validate the wrapper; FordA does not separate TS2Vec and T-Loss, see runs of D28/D32).
**Rationale:** User's decision (2026-10-08). The reproduction gives the reference; the full Paderborn dataset allows splits by bearing (leakage-safe, D33); the corrected version shows how much the code errors matter.

## 2026-10-08 — D36: Official TF-C reference is the 2023 code; our own corrected TF-C alongside
**Decision:** The official reference is the January 2023 version of the TF-C repository (submodule `external/tfc`, commit 9667582, folder `code/TFC`), run as distributed with only the changes of D37 and fixes needed to run (D19). The 2022 version is not used: it cannot run (model and loss imports commented out; the time-domain augmentation indexes arrays with floats, and its segment permutation fails with current NumPy), and its fine-tuning never loads the pretrained weights and never resets gradients, so it cannot be the code behind the published numbers either. In addition, our own TF-C is implemented as a separate, named method (D19) that fixes the problems found in the official code; its design is decided separately. Because no available official code reproduces the paper, D10 safeguard (1) (a composed version must first reproduce the official one) cannot be applied as written; how our version is validated is decided with its design.
**Alternatives considered:** The 2022 version (paper's architecture and loss, but cannot run; making it run needs interpretations of the authors' intent, i.e. a modified version). Only our own implementation, without an official run.
**Rationale:** User's decision (2026-10-08). The 2023 code is what is distributed and runs; its result shows what the official code gives, under both protocols of D37. Our version is the reference the corrections are measured against.

## 2026-10-08 — D37: How the official TF-C code is run for the reproduction (clean-protocol selection superseded by D43)
**Decision:** The adapter changes only what is needed to run the code (D19). The debugging subset is switched off (the adapter passes `subset=False`; the official files are not edited), so pretraining and testing use all windows. Validation and test scores are recorded after every fine-tuning epoch, and two numbers are reported from the same runs: (1) *official protocol* — the epoch with the best test accuracy, as the official code does, comparable with the paper; (2) *clean protocol* — the epoch with the best accuracy on FD-B's validation set (21 windows), test used once for that epoch. If the reproduction misses the target, a rerun with the debugging subset on is the first check.
**Alternatives considered:** Running exactly as shipped, debugging subset included. Reporting only the clean protocol (no comparison with the paper).
**Rationale:** Keeps the official behaviour while making the test-set selection visible; the gap between the two numbers is itself a result.

## 2026-10-08 — D38: TF-C reproduction target and seeds
**Decision:** Target: TF-C accuracy on FD-A → FD-B in the TF-C paper (arXiv 2206.08496, Table 5): 0.8934 ± 0.0379 over 5 runs; macro-F1 (0.9162 ± 0.0826) reported alongside. Criterion as D26: the published value within our mean ± 2 SD. Five seeds, matching the paper's five runs.
**Alternatives considered:** Three seeds as in D26.
**Rationale:** Same number of runs as the published result.

## 2026-10-08 — D41: Design of our own TF-C (`tfc`) (time-augmentation placeholders resolved by D42)
**Decision:** Our TF-C (`harness/methods/tfc.py`, reported as "TF-C (ours)") follows the paper (arXiv 2206.08496) and fixes the problems found in the official code (D36):
1. *Encoder:* the paper's CNN for both the time and the frequency branch: 3 blocks (Conv1d → BatchNorm → ReLU → MaxPool 2), kernel 8, strides 8/1/1, 32/64/128 channels; projector per branch 256 → 128 (Linear → BatchNorm → ReLU → Linear). Details the paper does not give (padding, pooling padding, dropout after block 1, bias) are taken from the 2022 code and written in the config.
2. *Frequency input:* full FFT magnitude spectrum (paper: full, symmetric spectrum; magnitude as in the code).
3. *Augmentations, redrawn for every batch.* Time: one of jitter / scaling / time shift / neighbourhood segments, chosen at random per window (paper); their parameters are not in the paper and are open (placeholders in the config; the run refuses to start until they are set). Frequency (user's design): one augmented spectrum per window in which E = 1 component is removed (amplitude set to 0) and E = 1 different component, among those with amplitude below α·max, is added (amplitude set to α·max), α = 0.5 (paper); both changes are applied to the same spectrum and symmetrically to bins k and N−k, so the augmented spectrum remains that of a real signal.
4. *Pretraining loss (paper):* λ(L_T + L_F) + (1 − λ)·L_C with plain NT-Xent (cosine similarity, τ = 0.2), L_C = Σ over the three pairs of (S_TF − S_pair + δ), δ = 1, no hinge (as in the paper), λ = 0.5.
5. *Optimisation:* gradients reset every step; Adam, learning rate 3·10⁻⁴, betas (0.9, 0.99) (code), weight decay 5·10⁻⁴ (paper), batch 64, 40 epochs.
6. *Fine-tuning (paper):* encoder and classifier trained jointly with cross-entropy + L_TF-C, using real augmentations of the fine-tuning windows; same optimiser settings; 40 epochs; no reloading of an earlier model during training. Classifier: 2-layer head (256 → 64 → classes).
7. *Epoch selection:* the epoch with the best macro-F1 on the target validation set (paper reports selection by F1); the test set is scored once, for that epoch.
8. *Metrics:* accuracy, macro precision, recall and F1, AUROC and AUPRC computed on the whole test set (not averaged over batches).
9. *Data:* all windows (no debugging subset).
10. *Validation (replaces D10 safeguard 1, see D36):* tests that our NT-Xent and L_C give the official functions' values; reproduction target D38 with the D26 criterion; an `encode()` function so the harness probes (D26) can be used later.
11. *Form:* one self-contained file; components are split out (D10 mode B) only when a second method needs them.
12. *Effect of the fixes:* official vs ours as a whole first; per-fix ablations only if the gap is large (D13).
**Alternatives considered:** A Transformer encoder used correctly (not in the paper). Frequency augmentation as in the official code (removal and addition computed separately and summed, so removed components reappear, and the spectrum is not kept symmetric). Selection by validation accuracy (as D37's clean protocol). Switches for every fix from the start.
**Rationale:** User's decision (2026-10-08). Follows the paper where it is specific; the frequency augmentation is corrected so that it describes a real signal and the removal actually removes.

## 2026-10-08 — D43: Clean protocol of the official TF-C run selects by validation macro-F1
**Decision:** In D37's clean protocol, the fine-tuning epoch is the one with the best macro-F1 on the target validation set (first one if tied), instead of the best validation accuracy. Supersedes that part of D37; the official protocol (best test accuracy) is unchanged.
**Alternatives considered:** Keeping validation accuracy (then the official run's clean number and our TF-C, D41, would be selected differently).
**Rationale:** User's decision (2026-10-08). Same selection rule as our TF-C (D41 item 7, the paper's F1), so the two clean numbers are comparable.

## 2026-10-08 — D42: Time augmentations of our TF-C
**Decision:** For each window, one of three time augmentations is chosen at random (paper: one augmented sample is selected per window): (1) *jitter*: Gaussian noise, standard deviation 0.1 (official code); (2) *scaling*: the whole window (per channel) multiplied by one factor drawn from N(1, 0.1) (our choice; neither the paper nor the code gives a usable value); (3) *permutation*, as described by TS-TCC: "splitting the signal into a random number of segments with a maximum of M and randomly shuffling them", with M = 5 (official code, max_seg) and the number of segments uniform in 1 … M (the text's maximum; the official code's draw only reaches M − 1); cut points drawn as in the official code. The paper's "time-shifts" are not used, and its "neighborhood segments" are not implemented as such: the paper names both but defines neither, and the code has neither. Supersedes the time-augmentation placeholders of D41 item 3.
**Alternatives considered:** Jitter and scaling only. All four augmentations named in the paper, with our own definitions of time shift and neighbourhood segments (rejected: no source defines them). The official code's scaling (an independent factor from N(2, 2) for every sample, i.e. multiplicative noise).
**Rationale:** User's decision (2026-10-08). Only augmentations with a source definition are used; the one value without a source (scaling) is marked as our choice.

## 2026-10-08 — D44: Official TF-C diverged on the full data: record divergence, and run with the debugging subset
**Decision:** The first official run (full data, D37) diverged: pretraining loss NaN from epoch 5 (seed 0), fine-tuning then crashed. (1) The script now records divergence as a result: if an epoch's pretraining loss is not finite, pretraining of that seed stops, the seed is marked `diverged` in results.csv without test scores, and the other seeds continue; summaries are over the non-diverged seeds, with the number of diverged seeds reported. (2) The official run is also made with the debugging subset on (D37's first check), config `configs/tfc_official_fd_subset.yaml`. The FD-A data contain no non-finite values (checked).
**Alternatives considered:** Only the subset rerun. Only recording divergence on the full data.
**Rationale:** User's decision (2026-10-08). (1) makes the failure measurable on the setting decided in D37; (2) tests whether the subset is what made the official code trainable (likely cause: gradients reset only once per epoch, so with the full data each step uses up to 127 accumulated batches, in an 842 M-parameter Transformer at learning rate 3·10⁻⁴; not verified).
