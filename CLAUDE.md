# CLAUDE.md

Research harness for baselining and developing self-supervised learning
methods for time series, with a focus on condition monitoring and
lubrication condition monitoring of ball bearings.

Start here: `README.md` (map of the repo), `STATUS.md` (what is done; partly
generated by `scripts/status.py`), `docs/` (current rules per method and dataset).

## Collaboration rules (D257)
- **Default to the standard, without asking.** For any choice (settings,
  preprocessing, windows, splits, probes, metrics, repo conventions) take the
  first that exists:
  1. a rule the harness already has (`docs/protocol.md`, the method's or
     dataset's card in `docs/`);
  2. the method's paper and official code, or the dataset authors' protocol;
  3. the common convention in the literature or in the standard tools
     (scikit-learn, PyTorch, uv, pytest, ...).
  Write the value and its source in the config or a code comment, and say in
  the reply what was chosen and from where.
- **Ask me only when** no standard exists; sources disagree in a way that
  changes results (paper vs code, several equally common conventions); a
  choice would depart from a standard; or it changes what a study can claim,
  costs a lot of compute, or cannot be undone (deleting data or runs).
  Then explain the dataset, target and setup first, give a recommendation,
  and ask one question at a time (independent questions may be batched).
- Never present an own choice as coming from a paper, code or convention.
- Never introduce silent defaults: every setting that affects results is
  written in the config (or code) with its source.
- **Decision log:** a D-entry for every decision I make and every departure
  from a standard (topic file under `decisions/`, line in `DECISIONS.md`,
  never deleted, replaced ones marked "Superseded by Dn"). Choices taken from
  a standard need no D-entry; they are recorded in the config comment and in
  the method's or dataset's card. Several chats write to the log: check the
  highest D-number in `decisions/` before adding one.
- **Keep the current-state views in step:** when a decision changes the
  current rule for a method, dataset or the protocol, update its card in
  `docs/`; after runs, regenerate the progress tables with
  `uv run python scripts/status.py`.
- **How experiments are built (D263):** start with the simplest version that
  answers the question; run it, look at it, then add refinements one at a time,
  only when I ask. Note proposed refinements as options instead of building them.
  Any extra beyond the standard runs (longer training, checkpoints, more seeds,
  variants) is done for all methods in a comparison or for none.
- **Checklist (D258):** the project to-do list is the claude.ai Project doc
  `claude/CHECKLIST.md`. When you finish a task, start or finish runs, record a
  decision, or hit a new open problem, update it yourself before ending your
  reply: read it, change only the lines about your work (tick items, add new
  open items with run folders and D-numbers, adjust "Next up", set "Last
  updated" and the highest D-number), and write the whole doc back. If the
  write is refused because another chat changed it, read it again and redo
  your edit. Don't restructure other sections; say in one line what you changed.
- Purely mechanical changes (formatting, typo fixes, behaviour-preserving
  refactors) may proceed, but must be mentioned.

## Code style
- Code must be minimal, easily readable and commented, so I can check it.
- No convoluted structures or abstractions for their own sake: prefer plain
  functions and simple classes over frameworks, registries or deep
  inheritance. Add structure only when it is clearly needed.
